---
name: AzadPanel protocol handoffs
description: Protocol-specific credentials and safe customer import flows for AzadPanel
---

AzadPanel returns an OpenVPN server address, username/password, locations, and `.ovpn` profiles, but not an OpenVPN Access Server import token or a customer-facing profile URL. OpenVPN Connect's import-profile deeplink uses the raw HTTPS URL after `openvpn://import-profile/`; do not percent-encode the nested URL. The profile endpoint must return `application/x-openvpn-profile`.

**Why:** OpenVPN's webauth RFC specifies the literal nested URL and exact profile MIME type. Percent-encoding the URL or returning the Provider's `text/plain` response type makes the Connect import invalid.

**How to apply:** Build the deeplink around a same-origin HTTPS profile endpoint; return the profile uncached, inline, with `application/x-openvpn-profile`, and never put Provider credentials in the link. Keep direct `.ovpn` downloads as a fallback. Do not add a one-time login handshake to the importer.

## WireGuard

An AzadPanel account is bound to its configured protocol core. Configure WireGuard as a distinct provider type/row with its own provider username/password; never reuse the OpenVPN provider credentials. Verify the selected core against AzadPanel's `/api/admin` response before protocol-specific provisioning. On `GET /api/user/{username}`, `403` means the account is outside this reseller's scope; `404` means it is absent. On an ownership collision, use a stable WireGuard-only provider username derived from the internal service ID, and persist that provider username for later profile reads. The official iOS app does not publish a `wireguard://` import scheme. AzadPanel supplies per-endpoint `.conf` files, not a customer import URL or cloud ID; WireGuard and AmneziaWG's Apple profile documentation supports `.mobileconfig` for iOS. A profile can contain multiple independent tunnel payloads; keep one server per tunnel instead of merging endpoints into a single multi-peer tunnel. For key-rotating renewals, keep top-level and per-tunnel profile identifiers and UUIDs deterministic by service, protocol, and server set so reinstallation updates the existing iOS profile.

**Why:** Mixing credentials across core-specific AzadPanel accounts can make provisioning fail or target the wrong protocol. Retrying a 403 as if it were an expired token repeats a forbidden request; the reseller API distinguishes this from a stale-token 401 and warns against excessive requests. WireGuard's returned config contains the private key, so exposing it in a URL or storing it as ordinary delivery metadata is unsafe. Apple's profile format installs separate tunnels together without treating them as one failover tunnel; reusing profile identity allows update-in-place, but iOS still requires customer confirmation in Settings and cannot silently refresh the app.

**How to apply:** Keep each protocol-specific provider connection super-admin managed and separate per-reseller access from provider credentials. Generic service provisioning and OpenVPN account selection must exclude WireGuard/IPsec-only rows; protocol-specific accounts run only through their dedicated permission-checked actions. Refresh provider tokens on `401`, not on `403`; after a user-ownership `403`, check the deterministic WireGuard alias once and create it only if that lookup returns `404`. Store the resolved provider username with the encrypted delivery so all later reads use the same account. Persist no provider credentials in delivery metadata; fetch and stream configs only after an explicit user action, with no-store headers. Offer `.conf` for manual import and `.mobileconfig` profiles for WireGuard/AmneziaWG on iOS, with one payload per server and the Settings confirmation step. Keep identifiers stable when the renewed config should replace the installed profile. Never promise an unsupported URL scheme or send provider credentials to the browser.

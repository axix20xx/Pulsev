PulseVPN — Full Production Audit, Repair, and UI/UX Redesign
ROLE
Act as a senior Android VPN engineer, React Native/Expo architect, Kotlin engineer, network-security specialist, QA lead, and mobile product designer.
You are working on the existing PulseVPN 1.0.28 codebase. Your task is to audit the complete application, repair confirmed defects, redesign the user experience, and validate the resulting Android release.
This is an implementation task, not a proposal. Inspect the source files, modify the actual code, run tests, build the application when the environment permits, and report verifiable results.
Do not replace the project with a mock application, a browser-only VPN interface, or a new prototype. Preserve the existing backend integration and native VPN engines unless a specific defect requires a carefully validated change.
1. NON-NEGOTIABLE REQUIREMENTS
Preserve the existing authentication API, subscription model, profile identifiers, API response contracts, and backend integration.
Preserve functional V2Ray/sing-box, OpenVPN, WireGuard, and AmneziaWG support.
Do not simulate VPN connections, traffic verification, server latency, subscription validity, or engine status.
Do not report a connection as successful merely because a VPN service started or a TUN interface was established.
Never disable TLS certificate validation, bypass Android VPN permissions, or weaken authentication to make tests pass.
Never expose subscription tokens, access tokens, passwords, UUIDs, private keys, or complete VPN configurations in logs, diagnostic exports, UI messages, or analytics.
Do not remove native modules, protocols, screens, or features simply to obtain a successful build.
Keep the application mobile-first and native Android compatible. Preserve Expo Router and the current native module architecture.
Use the existing repository’s package manager and lockfile. Do not migrate package managers.
Inspect the code before modifying it. Avoid blindly overwriting existing functionality or performing a wholesale rewrite.
If an issue depends on unavailable infrastructure, Android SDKs, credentials, or a physical device, document the limitation and provide a reproducible validation procedure.
Do not claim a test, APK build, or device validation succeeded unless it actually ran and passed.

3. PHASE TWO — FIX CONNECTION MANAGEMENT
3.1 Fix server-selection identity
Inspect app/connection.tsx.
Ensure the identity of a connection attempt includes every relevant selection:
Subscription/profile ID.
Protocol.
Selected server ID or canonical server identity.
Relevant configuration version.
Attempt generation.
Fix the V2Ray case where an existing connection may be considered the requested connection even after a different server is selected.
Do not compare only display names. Use stable IDs wherever possible.
Selecting server B while server A is connected must initiate the correct transition and ultimately connect to B, or show an explicit failure.
3.2 Prevent stale asynchronous callbacks
Use a consistent attempt-generation or cancellation strategy for all protocols.
Apply it to:
Connection promises.
Disconnection promises.
Permission requests.
Subscription/configuration fetches.
Traffic verification.
Timeout callbacks.
Reconnection attempts.
Delayed native events.
An obsolete attempt must not overwrite the state, selected server, error, or success indicator of a newer attempt.
Ensure unmounting or navigating away cannot cause unsafe state updates or leave unintended connection attempts running.
3.3 Define a single connection state machine
Use a single authoritative state model shared by the connection controller, home screen, server selection, and diagnostics.
Represent at least:
Disconnected.
Requesting permission.
Preparing configuration.
Connecting.
Establishing tunnel.
Verifying traffic.
Connected and traffic verified.
Connected but traffic unverified.
Reconnecting.
Disconnecting.
Failed.
Permission revoked.
Define valid transitions and handle duplicate or out-of-order events.
Do not allow two protocol engines to remain active simultaneously unless explicitly supported by the architecture. Disconnect the old engine and verify that it has stopped before starting another. Use bounded timeouts and explicit recovery if it does not stop.
On app startup, reconcile the native engine’s actual state with persisted preferences. Never restore a connected UI state from local storage alone.
3.4 Improve disconnect and reconnect behavior
Verify:
Repeated Connect and Disconnect taps.
Switching servers during connection.
Switching protocols during connection.
Connection timeout.
Permission cancellation.
Engine failure.
Android VPN revocation.
App backgrounding and foregrounding.
App process recreation.
Device sleep and wake.
Wi-Fi to mobile data transitions.
Mobile data to Wi-Fi transitions.
No-network recovery.
Rapid consecutive connection attempts.
The app must always offer a reliable way to disconnect.
3.5 Verify actual traffic
Use the existing native traffic-verification functionality where possible.
Distinguish:
Native service running.
Tunnel established.
Routes and DNS configured.
Traffic verification passed.
Traffic verification failed or timed out.
Provide a meaningful, bounded verification result. Do not equate an HTTPS test failure with proof that all VPN traffic is broken; explain the test limitation.
Do not show fabricated upload/download speeds or latency.

Phase 2 — Fix Bug A: sing-box Connects but No Data Transfers
Trace the complete packet path:
Android applications → Android VPN/TUN → sing-box inbound → routing rules → selected outbound → remote proxy server → response path → TUN → application.
Investigate and fix the following only where the code or logs demonstrate a problem.
A. TUN creation and descriptor lifecycle
Verify that Android VPN permission is granted.
Verify VpnService.Builder.establish() succeeds and returns a valid descriptor.
Confirm that the descriptor is transferred to sing-box using the integration method required by the installed sing-box version.
Ensure the descriptor remains open for the required lifetime and is closed safely on disconnect.
Check for duplicated descriptors, premature closure, blocking reads, and native engine startup races.
Verify the TUN interface is actually receiving and returning packets.
B. Routing and outbound selection
Inspect the generated sing-box configuration against the schema for the exact bundled core version.
Verify that routing rules select a valid outbound for ordinary internet traffic.
Confirm the configured proxy outbound has the correct server, port, authentication, transport, TLS, and protocol settings.
Detect invalid routing rules, unreachable endpoints, missing default routes, routing loops, and traffic incorrectly bypassing the proxy.
Confirm the proxy’s own outbound sockets are protected from being routed back into the same VPN where required by the Android integration.
Verify IPv4 and IPv6 handling. Do not advertise IPv6 support if the configuration cannot route IPv6 correctly.
Preserve intended split-tunneling and exclusion behavior.
C. DNS and MTU
Verify DNS requests reach the intended resolver and their responses return to the application.
Test whether direct numeric-IP connectivity works when domain resolution fails.
Check for invalid DNS routing rules, DNS loops, and unavailable resolvers.
Inspect MTU configuration for packet fragmentation or path-MTU problems.
Change MTU only when supported by diagnostic evidence; do not blindly apply a fixed value.
D. Service lifecycle
Check foreground-service startup, notification handling, Android VPN service declarations, permissions, and process lifecycle.
Ensure the native engine remains running after connection success.
Prevent duplicate engines, stale TUN descriptors, and concurrent VPN sessions.
Ensure disconnect and reconnect release resources correctly.
Respect Android’s one-active-VPN limitation and handle competing VPN sessions clearly.
E. Traffic-based connection status
Do not report a healthy connection solely because the TUN interface exists or the native engine started.
Implement a reliable connection state model with separate states for:
Disconnected
Requesting permission
Connecting
Tunnel established
Checking connectivity
Connected
Connected but no traffic / degraded
Reconnecting
Disconnecting
Error
Use a bounded connectivity probe with a timeout. Distinguish tunnel establishment from successful internet connectivity.
Avoid treating a single failed probe as definitive proof that the VPN is broken. Support retries and meaningful diagnostic errors.
Phase 3 — Fix Bug B: OpenVPN UI Stuck on Not Connected

If the tunnel is not actually connected, fix the native failure rather than masking it with a UI state change.
Phase 4 — Shared Connection-State Architecture
Implement or improve a single source of truth for connection status across supported protocols.
Requirements:
Separate each protocol’s native lifecycle from shared UI state.
Tag connection attempts with unique IDs or equivalent lifecycle guards to reject stale events.
Prevent callbacks from a previous protocol session from overriding the current session.
Clean up native event subscriptions on unmount and disconnect.
Make repeated Connect and Disconnect operations safe and idempotent.
Handle app backgrounding, foregrounding, and unexpected service termination.
Do not report Connected before the native engine confirms the tunnel is established.
Do not report Internet Available unless the connectivity check succeeds.
Keep protocol-specific errors available for troubleshooting.
Do not force OpenVPN and sing-box to use the same native implementation. Share state semantics while respecting each engine’s APIs.

RULE 2 — FIX OPENVPN STATE REPORTING

Inspect OpenVPNThreadv3.java, especially its event() method.

Investigate the defect where unrecognized OpenVPN events default to IDLE and are passed to the service.

Implement these requirements:

* Unknown informational events must not change connection state.
* A real OpenVPN CONNECTED event must remain connected unless a legitimate subsequent state transition occurs.
* Authentication failures, TLS errors, fatal errors, reconnecting, and disconnection must be mapped explicitly.
* Native callbacks must be the primary source of connection state.
* Do not use the last line of a mutable log file as the authoritative state.
* Fix service binding and recovery timeouts so a failed bind cannot leave the application permanently stuck.
* Do not report connected merely because the service start method returned.
* Preserve valid OpenVPN profile directives and cryptographic behavior.

Add a regression test proving that an unknown informational event cannot reset a connected session.

RULE 3 — FIX V2BOX / SING-BOX TRAFFIC

Trace the full path from configuration parsing through the native service, libbox, Android TUN, routing, DNS, outbound proxy, and internet traffic verification.

Investigate:

* Whether libbox initializes successfully.
* Whether the selected configuration is valid for the actual bundled sing-box version.
* Whether the TUN descriptor is established and passed correctly.
* Whether IPv4 and IPv6 routes are installed correctly.
* Whether default routing works on the supported Android versions.
* Whether upstream sockets are protected from VPN routing loops.
* Whether DNS bootstrap resolution succeeds.
* Whether hostname-based server endpoints can be resolved.
* Whether the outbound connection succeeds after TUN establishment.
* Whether stale service state or concurrent connection attempts break routing.
* Whether unsupported subscription entries are incorrectly presented as connectable.

Do not treat a successful service start or TUN establishment as proof that internet access works.

Use a staged connection lifecycle:

1. Permission granted.
2. Native service started.
3. Core initialized.
4. TUN established.
5. Routes and DNS configured.
6. Outbound connection established.
7. HTTPS traffic verified through the intended VPN.

Use bounded timeouts, cancellation, useful error messages, and privacy-safe logs.

If a stage fails, report the failed stage and its actual error. Never return a fake CONNECTED status.

Inspect all implemented sing-box configuration converters, including VLESS, VMess, Trojan, Shadowsocks, Hysteria 2, TUIC, HTTP, and SOCKS. Check TLS, REALITY, WebSocket, gRPC, DNS, IPv6, and unsupported transport combinations.

The parser recognizes SSR links but the converter may not implement SSR. Either implement genuine compatibility with the bundled engine or clearly reject unsupported SSR configurations before connecting.

Do not silently alter protocols or ignore required configuration parameters.

RULE 4 — AUDIT WIREGUARD AND AMNEZIAWG

Inspect the real native implementations, not just the TypeScript wrappers.

Do not mark a connection successful merely because a native interface object exists. Distinguish interface active, handshake observed, and internet traffic verified.

Implement safe coordination across sing-box, OpenVPN, WireGuard, and AmneziaWG.

* Serialize native connection and disconnection operations.
* Prevent simultaneous attempts from competing for the Android VPN slot.
* Stop the previous engine before starting another.
* Confirm that the previous VPN has stopped.
* Cancel stale connection attempts.
* Ignore callbacks belonging to previous attempts.
* Handle rapid retries, repeated button presses, process recreation, permission denial, and network changes.
* Clear stale connection states after service death or disconnection.

A JavaScript-only check is not sufficient. Use native synchronization where appropriate.
